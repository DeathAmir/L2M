Contributing to L2M

Found a bug, have an API idea, or want to improve the docs? Contributions are welcome. Start with a focused issue or pull request so the change can be reviewed properly.

i
Before you start

L2M is actively evolving. Check the current source and open issues before building on an API or behavior that may still change.

Ways to contribute

!Report a bug

Include what you expected, what happened, steps to reproduce and relevant logs.

Open an issue ↗✎Suggest an improvement

Describe the problem your idea solves and a small example of the expected behavior.

Browse issues ↗⑂Send a pull request

Fix code, add a feature or improve documentation in a reviewable change.

View pull requests ↗⌘Explore the source

Read the implementation before proposing changes to API behavior.

Open repository ↗

Pull request workflow

  1. Open the repository and create your own fork.
  2. Clone your fork and create a branch for one change. Keep unrelated changes separate.
  3. Make the change and update the documentation if user-visible behavior or an API changes.
  4. Run the checks relevant to the files you changed. Include the commands you ran and their results in the pull request description. If you could not run a check, say so.
  5. Push your branch to your fork and open a pull request against DeathAmir/L2M:main.
  6. Explain the reason for the change, summarize what changed, and link any related issue.
Terminal · example workflow
git clone https://github.com/YOUR-USERNAME/L2M.git
cd L2M
git switch -c docs/improve-api-guide
# make your changes
git add .
git commit -m "docs: improve API guide"
git push -u origin docs/improve-api-guide

Replace YOUR-USERNAME and the branch name with your own. This is an example workflow, not a required commit-message convention.

A few things that make reviews easier

  • Keep pull requests focused and explain the reason behind the change.
  • Do not document a planned feature as if it already works. Check the current implementation first.
  • For bug reports, include the Minecraft version, NeoForge version, Java version, steps to reproduce and relevant log output.
  • For Lua API changes, include a small script showing how the new behavior is used.
  • Avoid committing generated build output, local configuration, credentials or personal files.
